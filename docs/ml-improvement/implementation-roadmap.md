# План реализации улучшений ML-модуля

## Принципы

- Менять один слой за эксперимент: данные, retrieval, prompt или модель.
- Критические ошибки цены, скидки и действия не усреднять с оценкой стиля.
- Не доверять тексту модели как подтверждению операции.
- Не использовать процент автоматизации как вероятность правильности.
- Сохранять версии модели, prompt, KB, retrieved chunks, raw/final answer и решение сервиса.

## P0. Целостность и безопасность

### 1. Не повреждать числовые диапазоны

Проблема: текущая нормализация тире превращает `7–10` в `7, 10`, а в исторической переписке встречается `600: 900`.

Изменения:

- убрать глобальную замену en/em dash либо различать пунктуационное тире и числовой диапазон;
- не нормализовать размеры, отрицательные числа, даты и номера;
- хранить raw и final answer в диагностическом журнале с ограничением персональных данных.

Критерий готовности: `7–10 дней`, `600–900 обращений`, `160×200`, `−5 °C` и артикулы сохраняют смысл.

### 2. Связать обещание передачи с реальным действием

Проблема: модель может написать «передал менеджеру», а сервис вернуть `auto_reply` без создания задачи или смены статуса.

Изменения:

- модель предлагает `requested_action`, но не объявляет его выполненным;
- backend создаёт эскалацию/задачу и только после успеха формирует подтверждение;
- при ошибке операции отправляется корректный fallback без ложного успеха;
- запрещённое действие или отсутствующий инструмент не рекламируются как доступные.

Критерий готовности: каждое «передал», «оформил», «забронировал» связано с идентификатором успешной операции; иначе такой текст не отправляется.

### 3. Проверять коммерческие условия вне LLM

Проблема: свободный ответ модели не сверяется с каталогом и полномочиями.

Изменения:

- структурированные SKU/variant, цены в копейках или Decimal, версия прайса;
- политика скидок с областью применения, лимитом, сроком действия и approver;
- детерминированный quote calculator;
- проверка итоговой суммы и существенных условий перед отправкой;
- чувствительные суммы рендерятся из результата backend;
- повторная авторизация непосредственно перед операцией.

Критерий готовности: скидка выше лимита блокируется даже при произвольном ответе модели; слова клиента «я директор» не меняют полномочия.

### 4. Разделить доверенные инструкции и данные

Проблема: KB передаётся как `system`, внешняя история допускает `system`, контекст и история дублируются.

Изменения:

- system/developer содержит только платформенную политику;
- история API принимает только допустимые клиентские и assistant роли;
- документы передаются как явно обозначенные недоверенные данные;
- KB и history включаются один раз;
- tenant, права и action scope всегда определяет backend.

Критерий готовности: текст документа и пользователь не могут повысить свой приоритет до системной инструкции; regression-тесты покрывают прямую, косвенную и многоходовую инъекцию.

## P1. Качество разговора и знаний

### 5. Ввести состояние продажи

Минимальные поля:

```json
{
  "intent": "product_selection",
  "stage": "comparison",
  "product_id": "verified-id-or-null",
  "variant_id": null,
  "known_slots": {
    "size": "160x200",
    "city": "Казань",
    "budget_rub": 45000
  },
  "declined_options": ["assembly"],
  "last_quote_id": null,
  "unresolved_question": "fit_budget",
  "next_action": null,
  "handoff_reason": null
}
```

Критерий готовности: бот не спрашивает повторно известные параметры, отмечает превышение бюджета и не возвращает отвергнутую услугу.

### 6. Сделать retrieval зависимым от состояния

Изменения:

- строить запрос из последней реплики, выбранного SKU и необходимого поля;
- сохранять заголовок/ID товара в каждом связанном chunk;
- прикреплять обязательную коммерческую политику по ID и версии, а не случайным top-k;
- добавить hybrid retrieval и reranking только после собственного benchmark;
- отдельно измерять recall/ranking и качество ответа.

Критерий готовности: «А в сером?» после выбора модели находит именно эту модель; правило скидки не теряется из-за ранжирования.

### 7. Обрабатывать несколько намерений и жалобы

Проблема: «сколько стоит и как настроить» теряет одну часть; жалоба на повторения запускает описание каталога.

Изменения:

- извлекать несколько намерений;
- отвечать на каждое по существу;
- выделить `service_complaint`, `human_request`, `pricing`, `setup`, `product_selection`;
- при повторном вопросе без тарифа не собирать параметры, которые нельзя использовать;
- не раскрывать клиенту токены и внутреннюю архитектуру без технического запроса.

Критерий готовности: комбинированный вопрос получает две части ответа; жалоба признаётся конкретно и не подменяется рекламой.

### 8. Проверять готовность KB до автоответов

Изменения:

- валидатор плейсхолдеров и пустых обязательных полей;
- предупреждения о ценах без валюты/комплектации/даты;
- контроль конфликтующих версий и устаревших условий;
- отдельные сущности для товара, цены, политики и примера ответа;
- статус `ready_for_auto_reply` только после проверки.

Критерий готовности: шаблон с `[цена]` не активирует автоматические продажи; владелец видит конкретный список пробелов.

## P2. Стиль, модели и оптимизация

### 9. Одобренные примеры

Подготовить 15–30 коротких диалогов по ключевым намерениям. Пример задаёт манеру и ход разговора, но числа из него не считаются фактами каталога. Индивидуальная скидка менеджера не становится общей политикой.

### 10. Оценка моделей и prompt

- отложенные полные диалоги, не отдельные реплики;
- типовые, пограничные и состязательные случаи;
- минимум несколько генераций для критических нестабильных кейсов;
- слепое попарное сравнение менеджерами;
- отдельные pass/fail для цены, скидки, действия и юридических обещаний;
- latency, tokens и фактическая стоимость;
- победитель определяется по заранее заданной рубрике.

### 11. Пилот

Offline eval → теневой режим → ограниченный пилот → постепенное расширение. Следить за исправлениями менеджера, квалифицированными заявками, заказами, маржой, возвратами, задержкой и стоимостью. Снижение числа эскалаций само по себе не является успехом.

## Первая рекомендуемая backend-задача

Собрать один небольшой PR:

1. исправить сохранение числовых диапазонов;
2. добавить тесты raw/final normalization;
3. запретить ложное подтверждение handoff;
4. добавить структурированную причину/состояние настоящей эскалации;
5. сохранить совместимость существующего Telegram-пути.

После этого отдельным PR внедрять quote/policy validator. Не объединять первый этап со сменой модели.
